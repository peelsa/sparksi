# Changelog

## Unreleased

- A native recipe role now also records `library_sha256`: the SHA-256 of each shared library its binary loads from its own build tree (found by reading the binary's needed libraries, RPATH/RUNPATH, including a loader's RPATH, and the role's `LD_LIBRARY_PATH`; a damaged ELF file is read as loading nothing; an older recipe that records only the binary gets its libraries once the binary still matches; system libraries are left out, and nothing is run or copied). Every plan and start checks the binary and those libraries on the Spark that runs the role in one call and refuses a changed or missing one with one sentence. A recipe folder with no mounted files now has a version too (the version also covers `recipe.toml`), so the recipe page shows its folder, version and each Spark's copy, and `sparksi recipes bundle --dry-run` shows the version the folder will get. A recipe key that is not a bare word, such as a library path, is now written quoted.
- `sparksi recipes tidy-backups` no longer looks inside a recipe folder's `files/` and `roles/`, so a carried file whose name has `.bak` in it stays in the recipe. `sparksi recipes bundle` refuses, with one sentence and before writing anything, a mounted file or a set of files too large for a recipe folder, and names `--keep` as the way out.
- A recipe folder file may be up to 16 MiB and the whole folder up to 64 MiB (was 64 and 256 MiB), on the controller and in the node agent alike, because a copy is decoded in memory on a Spark that may be next to a loaded model. The "recipe folder changed" refusal is now one sentence.
- Only one Load is set up at a time. A second click, a retry or another model's Load while a recipe folder is still being copied to the Sparks is refused with one sentence, instead of passing the same checks and starting twice.
- Once a model has a recipe folder, the library run (`sparksi run` and the Library Run button) and the library switch (pair and single seat) are refused with one sentence too, so no catalog launch command starts it by another route. Stop still works.
- `sparksi recipes bundle <model-id>` moves an older pinned recipe and the files it mounts into a recipe folder. It records image IDs, binary hashes and the KV reserve, and `--dry-run` writes nothing. `sparksi recipes tidy-backups` moves old `recipes.bak-*` folders and `*.bak*` files into `backups/<date>/`, only moving and never deleting.
- The recipe page shows a folder recipe's folder, version, file count and whether each Spark's copy matches, and the recipe list gives each recipe's `version`. Once a model has a folder recipe, its catalog launch command is hidden as a way to start it (the `custom` engine and a catalog service Start are refused). Stop still works.
- A recipe role can record `image_id` (Docker image ID) or, for a native role, `binary_sha256`. Every plan and start checks the Spark that runs the role and refuses a different build with one sentence. A recipe's `[memory] kv_reserve_gib` now wins over the model card's for the memory check; the card's value is the fallback.
- Before every start of a recipe that uses folder files, the folder is copied to each Spark the recipe uses and checked by hash. A file changed since the check, a copy that cannot be made, or an existing copy that differs refuses the start with one sentence, and nothing runs. A saved change makes a new copy and leaves the old one alone. A dry run shows each Spark's copy as match, missing, differs or unknown, and a run records the folder version it mounts.
- The node agent can copy a recipe folder to a Spark (`files_stage`) and check a copy against its manifest (`files_check`). A copy is written once under that Spark's recipe root in a temporary folder, checked file by file, made read-only and renamed into place. An existing copy is only compared, never rewritten. The agent can also read files under the mount roots (`files_read`) and hash one file (`file_sha256`), both read-only. These ops never run on the controller in place of a Spark.
- A save, dry run or load of a folder recipe checks its `@files/` and `@role/` sources as the Spark paths they become, reads a mounted start script from the folder, and reports the folder, version and manifest in the plan's `files` block. Starting such a recipe is refused until the copy to the Sparks is in place.
- A recipe folder's files are listed with their SHA-256, and the list's hash is the folder's version. In a recipe folder a mount source can be written `@files/<path>` (shared by every Spark) or `@role/<path>` (that Spark's own file under `roles/<role>/`), and it resolves to `<recipe_root>/<model-id>/<name>/<version>/` on the Spark that runs the role. Each Spark's `recipe_root` defaults to `~/.local/share/sparksi/recipes` and can be set per Spark in `[[nodes]]`.
- A recipe can now live in its own folder, `recipes/<model-id>/<name>/`, with `recipe.toml` next to the files it mounts (`files/` and `roles/<role>/`). Save writes inside the folder, Save as copies the whole folder, Rename moves it, and Delete moves it into `backups/<date>/deleted/` instead of removing it. Recipes in the older layout work as before.
- A Spark card for a process no Sparksi run owns, such as an engine started outside Sparksi, shows its client URL with Copy again, as a run does. The worker of a pair shows "Head endpoint" and the head's URL. Loopback and wildcard addresses are never shown.
- A two-Spark engine started outside Sparksi, with the same container name and port on both Sparks and no TP setting or -head/-worker suffix, now shows on both Spark cards instead of the worker reading "Nothing running".
- The node probe also checks the Spark's own tailnet address when a model port is closed on loopback, so a server bound only to that address is seen. Off-limits ports are never tried there. A port where a catalog row declares served names is asked `/v1/models`, so the served name can be matched.
- A library model served by an engine Sparksi did not start (its weights mounted by a running container, its served name answering, its catalog containers not running) now shows as serving with "Started outside a Sparksi run". Sparksi never stops, restarts or replaces it: Unload and Restart with changes are greyed, and library Stop, switch, run and stopping an unmanaged container are refused with a clear message.
- Added `sparksi config validate` and `sparksi config show`. `validate` checks `sparksi.toml` and exits 1 with each problem; `show` prints the settings in force as JSON with secrets redacted (keys such as `x-api-key`, `tokens` and `private-key`, and secret-named or signature URL parameters, also when percent-encoded, included).
- An unusable `sparksi.toml` (not TOML, not readable, not a regular file, larger than 1 MiB, nested too deeply, a bad node, a table written as a string such as `controller = "x"`, or a config path that cannot be worked out) no longer raises a traceback when Sparksi is imported. The problem is logged once. Every `sparksi` command except `sparksi config ...`, and also `sparksi-monitor`, now prints the message and exits 1 instead of running on the built-in example. A top-level table written as a string is now refused at load instead of failing later.

## 0.6.0

First public release.

- Added `sparksi serve`, a controller with a dashboard and HTTP API on the default port 7500, plus the `sparksi` CLI. Pages: Overview, Model Manager, Library, Archive, Tokens, Activity, Network, Options.
- All site values, including hosts, addresses, paths and users, live in `sparksi.toml` and the catalog. Examples use placeholder names and documentation addresses.
- Added a node announcer: a stdlib-only script per Spark that sends one UDP datagram with memory, GPU, temperature and serving state. It is configured by `SPARKSI_NODE_ID`, `SPARKSI_CONTROLLER`, `SPARKSI_ADVERTISE` and `SPARKSI_PROTECT`.
- `sparksi install-unit --print` prints a user unit and never enables or starts it.
- Added a node agent, stdlib only, whose configuration the controller sends with every request.
- Added launch recipes for vLLM, SGLang, TensorRT-LLM (two-node is experimental) and llama.cpp. The browser sends fields, never a command string; argv is generated and checked against allowed images, ports 8010-8099, the memory budget and refused docker flags.
- Pinned recipes keep an imported launch per role.
- Loads are memory-aware: each Spark's free memory is checked and the load waits on health for the recipe timeout, 1800 s by default.
- Mutating calls require the lock to be off or the unlock token.
- The controller listens on loopback plus one tailnet address, refusing 0.0.0.0, :: and * and any address in a deny list.
- Added optional protection presets: `[protect] presets = ["video-service"]` keeps a video service and its port 8188 off limits. This is off by default and turned on automatically for configs that still use older key names.
- Overview shows one shared resource chart with GPU, CPU, memory and temperature in Fahrenheit, serving models on the cards, and a fleet power estimate.
- The Archive page copies archived weights onto a Spark; the Library page lists weights per machine.
- Older config keys, env vars and API field names are still read for one release; `docs/config.md` lists them.
- CI runs ruff, pytest on Python 3.12-3.14, gitleaks, an identity guard and a stdlib-only check of the agent and announcer.
